CLI commands

eval Command

Validate, run, report, and score skill evaluation suites defined in skill-project.toml.

FastSkill 0.9.229 · Release · Documentation source

View Markdown

Overview

fastskill eval runs skill quality checks using prompts and rubrics under [tool.fastskill.eval] in skill-project.toml. Subcommands are validate, run, judge, report, score, and scorecard.

eval run requires an agent on PATH for the chosen --agent key. Known keys are aikit, claude, codex, cursor, gemini, and pi. A key is accepted only when its CLI is detected on the current machine, so a typo and an uninstalled agent both error with RUNTIME_UNKNOWN_ID, which lists what was detected. Use eval validate --agent <key> or --all to verify availability.

Usage

eval validate

Checks eval configuration and files (optional agent presence check).

OptionDescription
--agent <AGENT>Verify the given agent(s) are available; repeatable. Mutually exclusive with --all
--allVerify availability of every installed agent. Mutually exclusive with --agent
--model <MODEL>The model eval run will target; a judge declaring the same one is reported as self-preference
--format <FORMAT>table or json only (eval does not support grid/xml)
--jsonShorthand for --format json

Every [[judge]] in the checks file is validated from file content alone, so validate gives the same answer on a laptop and in CI. Errors: no resolvable model; neither or both of prompt / prompt_file (likewise for the system and retry pairs); an unknown {{variable}}; a cases id matching no case; duplicate criterion names; scale below 2; min_score outside [0, 1]; a prompt that never renders {{output_contract}}; any unknown key. Warnings: a prompt without {{rubric}}, and a judge sharing --model. Endpoint reachability and API keys are not checked here — judging checks those before its first request.

With --agent or --all, both outputs report each selected agent: the table prints one agent '<key>': available|unavailable line per agent, and the JSON document carries an agents object keyed by agent id ({"agents": {"claude": true}}). An unavailable agent is an error unless fail_on_missing_agent = false is set in the eval config.

eval run

Runs eval cases against an agent; writes artifacts under --output-dir.

--agent <key> (repeatable) and --all are mutually exclusive — passing both errors with RUNTIME_CONFLICTING_FLAGS. eval run requires one of them (passing neither errors with RUNTIME_NO_SELECTION).

OptionDescription
--agent <AGENT>Agent key(s) to run; repeatable. Required unless --all is given
--allRun against all installed agents. Mutually exclusive with --agent
--output-dir <DIR>Required. Directory for run output
--model <MODEL>Optional model override passed to the agent
--case <ID>Run only this case id
--tag <TAG>Run only cases with this tag
--format <FORMAT>table or json only
--jsonShorthand for --format json
--no-failExit zero even when the suite fails
--trials <N>Override trials_per_case from the config for this run (1–1000)
--threshold <F>Override pass_threshold from the config for this run (0.0–1.0)
--ciCI mode: the suite passes when its overall pass rate meets the threshold, instead of requiring zero failed cases
--no-isolationRun in the project root against the ambient agent environment (disables per-case isolation)
--judgeJudge the run after scoring it, with the judges the checks file declares. Same function as eval judge
--judge-model <MODEL>Override every judge's model, and record the override

Environment isolation

By default every case runs isolated: the skill next to skill-project.toml is deployed alone into a per-case scratch workspace, and the agent's user-level skill discovery is suppressed where the backend supports it (claude, codex, pi). Scores then measure the skill under test rather than whatever else is installed on your machine. Isolation needs a SKILL.md beside skill-project.toml and a [metadata].id naming the skill — missing either is a EVAL_ISOLATION_NO_SKILL error, not a silent fallback.

The summary reports what each run actually got (isolation: line in table output, isolation object in summary.json), and a failed case's scratch workspace is kept under <run-dir>/workspaces/ for debugging. Pass --no-isolation to restore the old inherit-everything behaviour.

Scores recorded before isolation existed were measured against the ambient environment — expect trigger rates to re-baseline on the first isolated run.

eval judge

Scores a completed run with the LLM judges its checks file declares. eval run --judge calls the same function right after the run's own scoring — there is one judging implementation, so a run judged either way is judged identically.

OptionDescription
--run-dir <DIR>Required. The per-agent run directory (<output-dir>/<timestamp>/<agent>)
--checks <FILE>Read [[judge]] from this file instead of the one the run recorded
--judge-model <MODEL>Override every judge's model, and record the override
--judge-parallel <N>Concurrent judge requests (1–1000); defaults to the run's recorded parallel
--rejudgeJudge again even when the same request already has a judgment
--ciCI mode: the suite passes when its pass rate meets the run's threshold
--format <FORMAT>table or json only
--jsonShorthand for --format json
--no-failExit zero on suite failure. Does not suppress a judge error

A judge is one native chat completion per trial — no agent, no tools, nothing injected that the judge's author did not write. Each exchange is recorded in full in trial-N/judgments.json, and the engine, never the model, computes every score from the reply.

Rewrites are additive: result.json, aggregated.json and summary.json keep every field they had, and a reader that predates the judge tier sees exactly what it saw before. Judging the same run twice asks nothing — a trial whose latest judgment carries the same request identity is skipped unless --rejudge.

A trial that errored is never judged: there is no answer to score, and it is reported as skipped rather than as a zero. A judge that could not produce a judgment exits the command non-zero even under --no-fail, because a missing measurement must not be reported as a score.

eval report

Summarizes a completed run directory.

--format <FORMAT>table or json only
--jsonShorthand for --format json

eval score

Re-scores saved artifacts without invoking the agent again.

OptionDescription
--run-dir <DIR>Required. The per-agent run directory (<output-dir>/<timestamp>/<agent>)
--format <FORMAT>table or json only
--jsonShorthand for --format json
--no-failExit zero on suite failure

eval scorecard

Folds many runs into named metrics and gates each on its own threshold, where eval report describes one run and eval score decides one run's verdict.

A scorecard reports each measurement's own rate rather than a suite pass rate. A case carrying both a skill-invocation check and a tool-call ceiling would otherwise report a budget overrun as a recall failure.

OptionDescription
--root <DIR>Required unless --from. Searched recursively for run directories (any directory holding a summary.json)
--metrics <FILE>Required unless --from. TOML file declaring the metrics and their thresholds
--format <FORMAT>table, json or html
--jsonShorthand for --format json
--no-failReport the numbers without failing on a metric below its threshold
--allow-mixed-judgesFold judgments from more than one judge identity into one metric
--allow-mixed-targetsFold runs against more than one (agent, model) pair into one scorecard
--allow-duplicate-casesFold runs that measure the same case id more than once
--from <JSON>Render an already-written scorecard JSON instead of reading runs. Repeat it to draw a progress section. Conflicts with --root and --metrics
-o, --output <FILE>Write the report here instead of to stdout
--no-reasoningLeave judge reasoning out of the report and out of its embedded JSON

The metrics file

Each [[metric]] selects cases by *-wildcard id pattern. Omitting cases selects every case.

check_rate is passing check results over observed check results, over trials rather than cases: a case passing three of five trials contributes 3/5. tool_calls_p95 is the 95th percentile of tool calls per trial, compared against a ceiling. judge_score is the mean of a judge's overall — or of one named criterion — over the latest judgment per trial.

Identity: what the numbers are about

A number whose provenance is gone cannot be compared with last month's, so the scorecard records four identities beside the metrics:

IdentityWhere it comes from
TargetThe (agent, model) pair each run recorded
Skillskill_git_sha and skill_dirty copied from the run, never recomputed from the working tree — and reported only when every run agrees
Benchmarksha256 over the metrics file and every file the declared suites select (checks.toml, prompts.csv and every judge prompt file)
JudgesEvery distinct judge_hash with the model, endpoint and sampling settings that produced it

Three guards refuse a scorecard that would average two different measurements together. Each names the offending values, and each has an override that records itself in the document, so a reader can see the mixing happened:

Refused whenOverrideRecorded as
A judge_score metric folds more than one judge_hash--allow-mixed-judgesmetrics[].mixed_judges: true
The runs under --root carry more than one (agent, model)--allow-mixed-targetsmetrics[].mixed_targets: true, no top-level agent/model
The same case id is measured by more than one run--allow-duplicate-casesEvery cases[] row keeps its own run_dir

--no-fail suppresses none of these: it says "report the numbers rather than gate on them", not "the numbers mean something they do not".

The JSON document

--format json emits a fastskill.scorecard/1 document: the identities above, the metrics and totals the table shows, and a cases[] array with one row per (run, case) carrying every check result and, per judge, the latest judgment per trial with each criterion's normalised score, answer and full reasoning. Nothing in a row is summarised — the run directories get deleted, and this document is what survives them.

The HTML report

--format html renders the same document as a page a reader opens months later: identity, the gates and their verdicts, the exclusions above as notes, the judges and their sampling settings, then one table per suite with every case, its checks and its judgments, reasoning folded behind a <details> after the first 600 characters.

It is one file. The fonts are embedded, the stylesheet is inline, and the only <script> is a <script type="application/json"> holding the scorecards the page was rendered from — so the page carries its own machine-readable source, and opens with no network. A run directory is linked only when it is still on disk; a link to evidence that was deleted is worse than no link.

Pass --from instead to render scorecard JSON that was written earlier — on another machine, or by CI. That mode reads no run directory at all, so it links none.

Two or more --from files add a progress section: one chart per metric, ordered by generated_at, with the gate drawn as a dashed line and every point where the verdict flipped ringed. Series are keyed by target, so two agents on the same benchmark are two lines. Every input must carry the same non-null benchmark.sha256 — a chart across two benchmarks plots two different measurements as one trend, and there is no override for it. Mismatched inputs fail with EVAL_SCORECARD_BENCHMARK_MISMATCH; a scorecard whose metrics file declared no suites has no hash to compare and fails with EVAL_SCORECARD_NO_BENCHMARK_HASH.

--no-reasoning removes judge reasoning from the tables and from the embedded JSON. It is for reports that leave the team that ran them.

What is excluded, and why

  • Errored trials. A trial with outcome error still carries check results, because the checks ran, over an empty trace. Every negative expectation and every tool-call ceiling passed there vacuously, so folding them would report an outage as perfect restraint. They are dropped from every rate and counted separately.
  • Not-observable checks. A check whose evidence the backend cannot produce records passed: false for older readers. It is excluded rather than counted as a failure.
  • Estimated cost. Only the vendor-reported figure is summed. When no trial reported one, the line reads "not reported" rather than $0.00.
  • Judge errors and excluded trials. A trial whose judgment errored contributes nothing to a judge_score — not a zero — and is counted in totals.judge_errors. A trial a gated judge could not judge is counted in totals.judge_excluded_trials.
  • Advisory judge rows. A judge:<name> row for a judge that does not gate never moves a check_rate. It is reported by the judge_score metric that names the judge.

A case whose every trial errored is named in the output, and a metric that matched nothing fails the command even under --no-fail: a mistyped case pattern would otherwise make a gate quietly disappear. Check results that no metric claims are named in a warning.
